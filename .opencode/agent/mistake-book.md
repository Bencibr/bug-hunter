# BUG 错题集（Mistake Book）

> 机制：每发现/修复一个真实 bug，**反思 → 归类 → 提炼同类排查点**，追加一条记录。
> 后续每一轮勘察时**优先通读错题集**，把其中的「同类排查点」当作主动排查清单，
> 去同类代码路径找类似 bug——靠历史教训，不靠运气。
> 与 `history`（根因去重，管"别重复报"）互补：错题集管**往哪挖**。

---

## 分类体系（10 大类）

| # | 类别 | 一句话识别特征 |
|---|------|----------------|
| 1 | **类型假设崩溃** | 代码假设字段是 str/int/None，实际是 list/dict/ISO字符串/枚举 |
| 2 | **取数方向/排序错** | `LIMIT+ASC` 取到最旧而非最新；顺序处理反了 |
| 3 | **脱敏/加解密失效** | 只脱敏顶层键；fail-open 把密文当明文/密钥泄漏到产物 |
| 4 | **状态一致性/竞态** | 平局自胜自败、运行中事件循环调用、并行消息互相覆盖 |
| 5 | **契约不匹配** | 生产者返回的键名/结构 与 消费者读取的 不一致 |
| 6 | **修复回归/漏同步** | 修复 A 打破 B；同根因只修了一处，另一处漏修 |
| 7 | **功能漂移** | 枚举/补全表没跟着新功能更新，CLI 支持但补全/表项缺失 |
| 8 | **验证盲区/静默放行** | 校验只看名字不看签名；单条坏数据拖垮整批；负缓存缺失 |
| 9 | **流/多事件丢结果** | 流式响应取第一个而非最后一个；progress 吞掉最终 result |
| 10 | **输入边界/正则** | 正则无边界吞掉邮箱/@提及；中句触发词剥离上下文 |

### [1] 字段类型假设太窄 → 解析崩溃
- 现象：对 `content`/`timestamp`/`task_type` 等字段直接 `float()`/`join()`/`.value`，遇到 list/ISO字符串/str 枚举即抛异常。
- 根因：解析层对"字段可能是多种形态"缺少防御；把"当前唯一调用方传入的类型"当成了"契约"。
- 反思：每处裸 `float()`/`"\n".join(x)`/`x.value`/`x["k"]` 都是潜在崩溃点；多模态/字符串枚举/脏数据是常态不是异常。
- 同类排查点：搜索代码里裸的类型转换与属性访问（`float(`、`int(`、`join(`、`.value`、`["timestamp"]`），重点看配置/消息/事件数据流入处。
- 实例：findings_round12（content 为 list）、round13（脏行 timestamp）、round5（ISO timestamp）、round7（字符串 task_type）。

### [2] 取最旧而非最新 → 恢复/续接丢最近消息
- 现象：会话/恢复路径用 `list_records(limit=N)`（timestamp ASC + LIMIT）取到"最旧 N 条"，续接的是一段对话开头而非结尾。
- 根因：分页默认升序的惯性；没意识到"LIMIT 取前 N"在 ASC 下是取最旧。
- 反思：凡"恢复/续接/回放最近状态"必查排序方向；limit 语义必须配 `ascending=False`。
- 同类排查点：搜索 `list_records`/`LIMIT`/`[:N]`/`.sort()`，凡恢复/续接/取最近场景核对是否取反。
- 实例：findings_round8（restore_tree）、round9（REPL 续接，同一根因第二处）。

### [3] 脱敏只做表层 / 加解密 fail-open → 密钥泄漏
- 现象：脱敏函数只检查顶层 key，嵌套 dict/list 里的 `api_key`/`Authorization` 原样保留进训练数据；解密函数在缺依赖时把密文当明文返回。
- 根因：脱敏/加密对"结构深度"和"依赖缺失"没做防御；默认 fail-open。
- 反思：凡是"导出/日志/序列化"路径的敏感字段处理，必须递归且 fail-closed（拿不准就当敏感）。
- 同类排查点：搜索 `_sanitize`/`_redact`/`decrypt`/`to_dict`/`export`/JSONL 序列化，检查递归深度与无依赖分支。
- 实例：findings_round16（嵌套密钥）、round20（无 fernet 返回密文）。

### [4] 竞态/并行导致状态自相矛盾
- 现象：同优先级并发动作 winner==loser（自胜自败）；运行中事件循环里调 `asyncio.run()`；并行 tool_call 消息互相覆盖只剩最后一个。
- 根因：对"同一把 key 的 max/min 返回首元素"、"已有事件循环"、"并行追加 vs 覆盖"缺少意识。
- 反思：凡是并行/并发/排序去极值，必须显式用元组次键破局并验证 winner≠loser；循环内跑同步驱动先查 running loop。
- 同类排查点：搜索 `max(`/`min(`/`sorted(`（并发仲裁）、`asyncio.run`（循环内）、`tool_calls`/`append` vs `=`（并行消息）。
- 实例：findings_round5（ConflictArbiter）、round15（drain_sync）、round8（tool_call 覆盖）。

### [5] 生产者/消费者契约键名不一致
- 现象：CLI 读 `total_tasks`，实际返回 `total_in_registry`；读 `result["result"]`，实际返回 `{stdout}`；消费者只在 should_proceed=False 时展示 caution。
- 根因：不同模块各写各的键名，没有对齐契约；警告通道的消费分支没覆盖全部返回值。
- 反思：跨模块读结构前先核对返回结构；"低置信度也要展示"这类分支最易漏。
- 同类排查点：搜索跨模块的 `["xxx"]`/`get("xxx")` 读取，对照生产者的 return dict；尤其 warning/caution/fallback 分支。
- 实例：findings_round7（task stats）、round7（cron stdout）、round18（caution 丢弃）。

### [6] 修复引入回归 / 同根因只修一处
- 现象：为排除邮箱给 `@` 引用加了路径形态过滤，反而拒绝 `@Makefile` 等无扩展名文件；同一取最近消息 bug 在 store 修了、REPL 续接漏修。
- 根因：修复时只考虑"要挡的坏输入"，没回归验证"合法输入仍可用"；同根因多处的修复没全量同步。
- 反思：任何修复都要问"会不会误伤合法输入"；找到根因后 grep 全仓找同类代码点一次修完。
- 同类排查点：修改正则/过滤逻辑后，跑一遍合法/边界双清单；修根因时 grep 关键词全仓同步。
- 实例：findings_round11（@Makefile 回归）、round9（REPL 漏修）、round5（experience_workshop 漏同步）。

### [7] 枚举/表项漂移，CLI 支持但补全/查询缺失
- 现象：`MEMORY_SUBCOMMANDS` 没含新增子命令，Tab 补全对 `pending/confirm/reject` 无候选。
- 根因：手维护的枚举/补全表与功能演进脱节。
- 反思：凡是"列出可用项"的静态表（补全、白名单、菜单），都要与真实注册表/路由对齐。
- 同类排查点：搜索硬编码的 `[...]` 子命令表、`completion_items`、白名单，与 CLI 路由逐一比对。
- 实例：findings_round6（memory 补全器）。

### [8] 校验看名字不看行为 → 每次必崩的"已验证"工具
- 现象：入口校验只看函数名与 AST 沙箱，不校验签名能收单位置 dict 参数；`def execute():`（无参）照样注册为可用工具。
- 根因：校验停留在"静态表面"（名字/语法），没做"最小行为验证"（真实调用一次）。
- 反思：凡"注册/晋升为可用"的校验，能真调用一次就真调用一次；静态通过 ≠ 可用。
- 同类排查点：搜索 `_validate_`/`validate_entrypoint`/probation/晋升路径，检查是否含真实调用。
- 实例：findings_round17（CodegenToolCreator）。

### [9] 流式/多事件只取第一个 → 丢最终结果
- 现象：MCP streamable-http 一次响应含 progress 通知 + 最终 result，解析到第一个 dict 就 return，把 progress 当结果。
- 根因：假设"一个响应一个 JSON"，没处理"多个事件需要选带 id 的最后一个"。
- 反思：流式解析必须区分"通知"与"应答"，取最后一个带 id/result 的，而非第一个。
- 同类排查点：搜索 SSE/流式解析 `json.loads` 循环、`return` 在循环内过早退出、`data:` 处理。
- 实例：findings_round14（_parse_sse_body）。

### [10] 正则/触发词无边界 → 吞掉合法内容或剥错上下文
- 现象：`@([^\s@]+)` 把邮箱 `me@example.com` 当文件引用；中句触发词把触发词前的整段真实指令剥掉，只剩「周五交」。
- 根因：正则/字符串查找没加边界断言，切割逻辑按"找到即截断"而非"只剥触发词本身"。
- 反思：任何 `find`+`strip` 组合都要区分"定位"与"切割范围"；正则先加 `(?<!\w)` 词边界。
- 同类排查点：搜索 `re.`（无 `\b`/`(?<!` 的）、`.find(`+`.strip(`/切片截断、触发词提取逻辑。
- 实例：findings_round9（邮箱吞并）、round4（中句触发词剥离）。

### [11] 单条脏数据拖垮整批处理
- 现象：持久化文件/事件库里一条坏行，让整个 `_load`/`replay`/`replay_topic` 批量处理崩溃，坏条目之后全丢。
- 根因：批量循环里没有逐条 try/except 的"部分失败恢复"，一条坏即全坏。
- 反思：凡批量读（加载/回放/迁移/同步），必须逐条容错 + 跳过坏行 + 告警，好行照常返回。
- 同类排查点：搜索批量 `_load`/`replay`/`for ... in rows`/`list_records` 的解析循环，确认有无逐条防护。
- 实例：findings_round13（事件回放）、round4（scheduler _load）。

## 每轮使用规则（写进 agent 记忆）

1. **勘察前必读**：进入全量发现前，先通读本错题集，把「同类排查点」合并成本轮主动排查清单。
2. **发现后反思**：每确认一个真实 bug，按上面 10 类归到最贴近的一类，追加一条错题记录（现象/根因/反思/同类排查点/实例）。
3. **归类不重复**：同一根因不同文件算一条（合并）；新类别出现时在分类表新增。
4. **跨轮避旧**：错题集条目是"去哪挖"的线索，不是"去复现旧 bug"——新发现必须与 `history` 根因去重后才计命。
